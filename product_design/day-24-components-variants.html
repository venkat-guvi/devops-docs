Part 1: Introduction to Components

What is a Component in Design Systems?

A component is a reusable, self-contained building block of a user interface. It encapsulates a specific UI pattern - its structure, appearance, behaviour, and states - into a single, manageable unit that can be placed anywhere in the product.

A component is not just a Figma frame with a name. It is a living specification: it defines not only how something looks, but how it behaves across every possible state and context in which it can appear.

Why are Components the Foundation of Scalable UI ?

Design Without Components

Design With Components

Every button is drawn fresh for each screen

Every button is an instance of the master Button component

Updating the button style requires touching 200+ screens

New team members copy the nearest button they can find

Consistency erodes with every new screen and every new designer

Consistency is enforced by the system, not by vigilance

A rebrand requires a full design audit and re-delivery

A rebrand requires updating token values - changes propagate automatically

Part 2: From Screens to Components - The Mindset Shift

From Screens to Components

The traditional design workflow starts with screens. You open Figma, create a frame the size of the device you are targeting, and start laying out content. This approach feels natural because it mirrors how users experience the product - as screens.

But it produces fragile design systems. When you design screen by screen, you make countless micro-decisions (this button is 40px tall, this card has 16px padding, this heading is 24px bold) that are not recorded, not shared, and not enforced. Every new screen requires making the same decisions again - and each time, drift occurs.

The Hidden Costs of Screen-First Design

Inconsistency compounds: each new screen introduces new micro-decisions that contradict previous ones

Handoff is ambiguous: engineers receive multiple versions of the same element with no defined master

Iteration is expensive: changing a pattern that appears across 20 screens requires opening and editing 20 frames

Onboarding is fragile: new designers find the nearest existing screen and copy from it - propagating all existing inconsistencies

Accessibility is deferred: when every screen is bespoke, accessibility is checked only at the end - when the cost of fixing it is highest

The design file becomes a museum: historical screens that no longer represent the product sit in the same file as current work, creating confusion

Shifting the Mindset: Screen to Reusable Blocks

Part 6: Variants in Components

What are Variants and Why They Exist

A variant is a defined version of a component that differs from the base version in one or more properties. Variants exist because the same UI pattern must serve different contexts, communicate different states, and adapt to different constraints - without being a different component.

The Complete Variant Reference

Variant

Specification

When to Use

Size - Small

Height: 28-32px, Font: 12-13px, Padding: 8px 12px, Icon: 16px

Dense UIs, data tables, inline actions, toolbar buttons, tag actions. Anywhere space is constrained.

Size - Medium

Height: 36-40px, Font: 14px, Padding: 10px 16px, Icon: 20px

The default size for most UI contexts. Forms, cards, modal footers, settings pages.

Size - Large

Height: 44-48px, Font: 15-16px, Padding: 12px 20px, Icon: 24px

Primary CTAs, hero sections, onboarding flows, empty state actions. When the action must be unmissable.

Type - Primary

Filled background with brand primary colour. White label. High visual weight.

The main action on any view. One primary button per view - never two competing primary buttons.

Type - Secondary

Filled background with lower-priority colour (grey or secondary brand). Moderate visual weight.

Supporting action alongside primary. Cancel, Save Draft, Add Another.

Type - Ghost

No background. Coloured label and border-radius only. Low visual weight.

Tertiary actions, destructive confirmations where weight should be low, inline text actions.

Type - Outline

Transparent background. Coloured border. Coloured label. Medium-low visual weight.

Alternative to secondary. Popular in card footers, filter controls, and segmented selections.

Type - Danger / Destructive

Red background or red border/label. Signals irreversible action.

Delete, Remove, Deactivate. Dangerous actions that cannot be undone. Must be separated spatially from cancel.

Type - Link

No background, no border. Coloured underlined label. Inline text behaviour.

Inline actions within body copy. Footer links. Breadcrumb-style navigation within content.

State - Default

The component at rest. No user interaction has occurred.

All components must have a defined default state. This is the starting point for all other state definitions.

State - Hover

Subtle background change or opacity shift indicating interactivity. Not visible on touch devices.

Must be distinct from default but not dramatic. Use 10-15% background opacity increase or lightness shift.

State - Active / Pressed

Stronger visual depression: darker background, scale transform (0.97-0.99), or shadow removal.

Provides tactile feedback for clicks and taps. Duration: 100-150ms. Must be distinguishable from hover.

State - Focus

Visible focus ring for keyboard navigation. Required for WCAG 2.1 AA compliance.

3px offset focus ring in a high-contrast colour (often the brand primary or a system focus blue). Never remove outline:none without replacement.

State - Disabled

Reduced opacity (0.4-0.5) and non-interactive. Cursor: not-allowed.

Never hide disabled components. Users need to see that the action exists but is unavailable - and ideally understand why.

State - Loading

Spinner or skeleton replaces label. Component remains in place and size-locked during loading.

Prevent double-submission by disabling the component during loading. Preserve exact component dimensions during the loading state.

State - Error

Red border, red icon, error message below. Applicable to inputs, selects, and file uploads.

Error message must be adjacent to the field, not grouped at the top of the form. Use aria-describedby to associate error with field.

State - Success

Green indicator or checkmark. Typically transient - fades or transitions after 2-3 seconds.

Success states confirm completion. Use sparingly - only for actions where confirmation is necessary to prevent re-submission.

Managing Variants at Scale

The danger of variant systems is exponential growth. If a button has 5 types, 6 states, 3 sizes, and 4 icon positions, the complete matrix is 5x6x3x4 = 360 variants. Building and maintaining 360 individual variant frames is unsustainable.

How Variant Sets Become Unmanageable

Exponential growth: adding one new property dimension multiplies the entire variant set

Maintenance debt: every design system update requires propagating to potentially hundreds of variant frames

Cognitive overload: a component with 200+ variants is not usable - designers cannot find what they need

Naming collapse: with too many variants, the naming convention breaks down and variants cannot be distinguished by name

Real example: A navigation component with 4 orientations x 3 densities x 5 states x 4 active-item styles = 240 variants. This is not a component system. This is a museum.

Balancing Flexibility vs Simplicity

Too Much Flexibility

Too Much Simplicity

Component accepts every possible variation without constraint

Component is completely rigid - only one possible form

No variant rules - designers can configure any combination

Every new context requires a new component

Result: Every instance looks different despite using the same component

Result: Component library proliferates with near-identical components

System becomes a tool for inconsistency, not against it

System becomes bureaucratic - designers work around it rather than with it

The component is "flexible" but provides no design direction

The component is "simple" but does not serve the actual variety of needs

Part 7: Component Consistency and Common Mistakes

Component Consistency - Maintaining Uniform Behavior Across the Product

Consistency in a component system means that the same component behaves identically in every context where it appears. A Primary Button in the onboarding flow must look and behave exactly like a Primary Button in the settings page. The system enforces this - not designer vigilance.

Four Dimensions of Component Consistency

Visual Consistency: The same component variant looks identical in every screen where it appears. No ad-hoc colour overrides, no manually adjusted padding, no locally detached instances with bespoke styling.

Behavioural Consistency: Hover, focus, active, and disabled states behave the same way across all instances of a component. Users develop accurate mental models because the component always responds in the same way.

Naming Consistency: Component names follow the same convention across the design file and the codebase. Button/Primary/Default in Figma is ButtonPrimary in React. The names are different in format but map 1:1.

Documentation Consistency: Every component has the same documentation structure: description, usage guidelines, variant list, do/do-not examples, accessibility notes, and responsive behaviour. No component gets more or less documentation than another.

Part 8: Breakdown of a Real Product Component - The Button System Evolution

The button is the most common component in any UI - and the most revealing indicator of a design system's maturity. Tracing the evolution of a button from its earliest form to a production-ready design system component is the clearest way to understand what a component system actually accomplishes.

Key Observations from the Button Evolution

Every design system starts the same way: with a hardcoded, inconsistent, undocumented button. The journey is the same for every team that builds a real system.

The greatest jump in value is from Stage 2 (Shared Style) to Stage 3 (Basic Component). The moment you create a real component, you unlock single-source updates.

The greatest jump in scalability is from Stage 3 (Basic Component) to Stage 4 (Variants Added). This is when the component stops being a shortcut and becomes a system.

Token integration (Stage 6) is the moment design and engineering truly synchronise. Before tokens, the design system is a reference. After tokens, it is a source of truth.

Documentation (Stage 7) is what makes the investment compound. Every hour spent on documentation saves dozens of hours of team confusion over the product's lifetime.

Most teams stop at Stage 3 or 4. Teams with mature products reach Stage 6 or 7. The gap between these stages is where most design inconsistency lives.

💡 Key Takeaways

Components

Self-contained, reusable UI building blocks with defined structure, properties, and behaviour. The atomic unit of a design system.

Scalability

Components are the foundation of scalable UI. Without them, every new screen is a new problem. With them, every new screen is an assembly of solved problems.

Mindset Shift

Design component-first, not screen-first. Identify repeating patterns first. Build components. Assemble screens from components.

Component Anatomy

Every component has 6 layers: Container, Content Area, Label, Icon, Action Target, and Feedback Indicator. Every layer has rules.

Component Types

Basic (buttons, inputs, icons) and Complex (cards, modals, navigation). Know when to build atomic vs composite components.

DRY in Design

Every pattern has one source. Instances everywhere. No copy-paste. No detached instances. One update propagates to the entire product.

Variants

The defined set of all legitimate forms a component can take. Size, Type, and State are the three primary variant dimensions.

Variant Management

Avoid variant explosion through boolean properties, slot architecture, state overlays, and composition. Design for real use cases, not speculative ones.

Consistency

Visual, behavioural, naming, and documentation consistency together make a component system trustworthy and adopted.

Button Evolution

A component evolves through 7 stages: Hardcoded > Shared Style > Basic Component > Variants > Size System > Token Integration > Documentation. Most teams stop too early.
