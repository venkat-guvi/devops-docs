ARCHITECTURE & USER FLOWS

Part 1: Organizing Product Information

Duration: 20 minutes

1.1 What is Information Architecture?

Information Architecture (IA) is the blueprint of your product. It is how you organize, structure, and label information so users can find it. IA answers: What information exists? How should it be organized? How should users navigate to it?

"Information Architecture is about creating a blueprint that helps users navigate seamlessly through content without getting lost." — Peter Morville

1.2 IA is Invisible When It Works

Good IA feels natural. A user never thinks "Where would this be?" They just find it. Bad IA is exhausting. Users click, backtrack, click again, get frustrated, leave. The architecture failed silently.

Good IA Looks LikeBad IA Looks Like
User knows where to find thingsUser gets lost and uses search as a crutch
Labels make sense (no jargon)Labels are confusing or don't match how users think
No dead-ends or circular pathsNavigation loops back on itself; hard to go "back"
Categories are mutually exclusive (item is in one place, not three)Items appear in multiple places with no consistency
Primary information is easy to find; advanced options are tucked awayEverything is equally prominent; overwhelming choices
Structure mirrors user mental modelStructure made sense to the designer, not to the user

1.3 IA Fundamentals: The Layers

LayerWhat It IsExample
Content InventoryAn audit of all information in your product. Every page, form, report, data type.E-commerce site: product pages, category pages, cart, checkout, reviews, wishlists, orders, user account, returns, FAQs
Organization SchemeHow you categorize and group information. By type? By user goal? By audience?Product categories: Electronics, Clothing, Home. OR by use case: Office supplies, Camping gear, Daily wear
Navigation StructureHow users move through the information. Hierarchical? Search-driven? Hub-and-spoke?Top navigation shows main categories. Sidebar shows subcategories. Search is always available.
Labeling SystemThe words you use for categories, buttons, links. Must be clear and match user mental models.Button says "View Order History" not "Legacy Transactions". Link says "Shipping Info" not "Logistics".
FindabilityCan users find what they need? Through navigation? Search? Browsing?User searching "return a gift" should find returns policy. User looking at shoes should see size guides.

1.4 Information Organization Schemes

SLIDE: How to Organize Information
Hierarchical: Most common. Categories break into subcategories, which break into items. Top-down tree structure.
Sequential: Step-by-step path. Used for onboarding, wizards, checkout flows. User moves forward, can go back.
Database/Faceted: Items tagged with multiple properties. User filters by tags to narrow down. (e.g., Amazon: Filter by Brand, Price, Rating, etc.)
Search-driven: User types a query, system returns results. Works when users know what they want.
Hub-and-spoke: Everything connects to a central hub. Dashboard-style. Every section is equally distant from home.
Social/Network: Users follow other users or content. Recommendations and feeds drive discovery. (e.g., Twitter, Instagram)

1.5 Content Audit: The First Step

Before you can organize information, you must know what information exists. A content audit is a spreadsheet of every piece of content in your product.

How to Conduct a Content Audit
List everything: Every page, form, modal, data type, message. Go URL by URL (or screen by screen in mobile apps).
Categorize each item: What type of content is this? (Product listing, Form, Error message, Help text, etc.)
Note the owner: Who maintains this content? Design? Engineering? Product? Support?
Identify gaps: What should exist but does not? (Help pages, Returns policy, etc.)
Spot redundancy: Is the same information in multiple places? (Same help topic on two pages?)
Prioritize: Mark items as: Critical (must include), Important (should include), Nice-to-have (can wait)
Use the audit to inform IA: High-priority items should be easy to find. Low-priority items can be tucked away.

Part 2: User Journey Mapping

Duration: 20 minutes

2.1 What is a User Journey Map?

A user journey map shows the path a user takes to accomplish a goal, including all the touchpoints (places where they interact with your product), their actions, their thoughts, and their emotions. It reveals frustration points and moments of delight.

SLIDE: Anatomy of a User Journey Map
Persona: Who is this user? (e.g., "Sarah, 32, works in marketing, shops online 2x per week")
Goal: What does the user want to accomplish? (e.g., "Buy a birthday gift for her partner")
Stages: Major phases of the journey (e.g., Research → Compare → Select → Checkout → Delivery)
Touchpoints: Where user interacts with your product (e.g., Browse products, Read reviews, Check shipping)
Actions: What the user does (e.g., Adds item to cart, Enters zip code to check delivery time)
Thoughts: What the user is thinking ("Is this the right size?" "Does it ship internationally?")
Emotions: How the user feels at each step (Excited → Confident → Anxious → Relieved → Happy)
Pain points: Where does the user get frustrated? (e.g., Cannot filter by price, Shipping cost is a surprise)
Opportunities: Where can you improve? (e.g., Show delivery date earlier, Add size comparison tool)

2.2 Creating a Journey Map

Steps to Build a Journey Map
Start with research: Interview 5-10 real users. Ask about their goal, their process, frustrations, emotions.
Create a persona: Synthesize the interviews into a user archetype. Age, role, goals, pain points.
Map the happy path: The ideal path from goal to completion. Where does the user succeed?
Map the reality: What actually happens? Where does the user deviate? What causes delays?
Add emotions: Use a line graph to show emotional highs and lows. Where is the user frustrated? Where are they delighted?
Identify pain points: Mark every moment of friction, confusion, or disappointment.
Spot opportunities: For each pain point, brainstorm how design can help.
Share with your team: A journey map should drive decisions. Review it in product reviews, design reviews, sprint planning.

2.3 Identifying Pain Points & Opportunities

2.3 Identifying Pain Points & Opportunities

Common Pain PointsSolutions IA Can Provide
User cannot find product category (wrong mental model)Reorganize categories to match how users think (user research needed)
User does not understand difference between optionsAdd comparison feature or clearer descriptions
User gets lost; cannot find way back to previous stepImprove navigation, add breadcrumbs, show progress
Too many clicks to accomplish goalShortcut the path, remove unnecessary steps
User does not know if they made a mistakeAdd confirmation messages, clear feedback
Information is scattered; user must search multiple placesCentralize information on one page or surface
Users expect feature/information that does not existAdd the feature or make its absence very clear

Part 3: User Flows & Task Flows

Duration: 20 minutes

3.1 User Flows vs Task Flows

A user flow shows the big picture: how a user accomplishes a goal from start to finish. A task flow zooms in on a specific step: the exact actions the user takes in a particular part of the flow.

User Flow (Big Picture)Task Flow (Step Detail)
Shows the complete path to a goalShows exactly what user does in one step
Zoomed out: all the major stepsZoomed in: every click, every form field
Example: How user returns a productExample: How user initiates a return request
Used in: Product planning, conversation with stakeholdersUsed in: UI design, engineering handoff, detailed testing
Usually 5-10 major stepsUsually 8-15 micro-steps
Includes decision points (Does return qualify? Yes/No)Includes form validation, error handling, confirmations
Focus: Removing unnecessary stepsFocus: Making the step as clear as possible

3.2 Mapping a User Flow

A user flow is a diagram showing the path from start to goal. It includes decision points where the path might split.

SLIDE: User Flow Components
Start node: Where does the user begin? (Logged in on dashboard? On homepage? In an email?)
Steps (rectangles): Major actions the user takes (Search product, Add to cart, Enter shipping address)
Decision point (diamond): A question with yes/no answer. If yes, go one way; if no, go another.
End node: Goal achieved. User has successfully completed the flow.
Alternate paths: What happens if something fails? (Payment declined, Address not found, etc.)
Loop back: Can users redo a step? (Change quantity before checkout? Edit cart?)
Dead ends: Paths that do not lead to goal completion (User abandons, asks for help, escalates to customer service)

3.3 Common Flow Patterns

Flow TypeWhen to UseStructureExample
Linear FlowOnboarding, forms, checkout. Step A → B → C → DOne path, no branchesSignup: Enter email → Create password → Verify email → Done
Decision FlowMost real flows. User choices split the pathStart → Decision → Path A or Path B → EndReturn item: Approved → Refund shipped vs Rejected → Denied
Loop FlowActions that repeat. Browse → Select → RepeatUser can do the same action multiple timesShopping: Browse products → Add to cart → Browse more → Checkout
Alternative PathError handling, fallbacksHappy path + alternative if something failsForget password: Has email → Send reset vs No email → Verify identity
Conditional FlowDifferent paths for different user types or dataPath depends on user role, account type, etc.Checkout: Registered user → Fast checkout vs Guest → Full form

3.4 Red Flags in Flows

When Your Flow Needs Redesign
Too many steps: Can you reduce from 8 steps to 5? Every step you remove improves conversion.
Too many decision points: If user must answer more than 2-3 questions, it feels like an interrogation.
Loops back to start: If user must begin again after an error, it is friction. (Bad: Payment fails → Back to beginning. Good: Payment fails → Stay on payment form, try again)
No error handling: What happens if validation fails? Form just clears? Shows generic error? Include error states in flow.
Unclear decision criteria: If a decision point is "Is user happy?" that is vague. Make it concrete: "Did user complete onboarding?" Yes → Show dashboard. No → Show onboarding.
Dead ends: Paths that abandon the goal. (User asked for help → Contacted support → Took days → Eventually refunded. Better: Offer instant solution.)
Overly complex: If your flow needs a legend to understand, it is too complex. Simplify.

Part 4: Structuring Navigation & Screens

Duration: 25 minutes

4.1 Creating a Sitemap (Information Hierarchy)

A sitemap is a visual representation of your product's structure. It shows how all pages/screens relate to each other. It is the physical manifestation of your IA.

SLIDE: Sitemap Structure
Home: Usually at the top. All major sections branch from home.
Primary sections: 5-7 main categories. (For an e-commerce: Products, Deals, Account, Support, About)
Secondary pages: Subcategories under each primary section. (Under Products: Electronics, Clothing, Home)
Tertiary pages: Specific pages. (Under Electronics: Computers, Phones, Accessories)
Utility pages: Always accessible. (Search, Settings, Help, Contact, Terms)
Footer links: Important links that do not fit in main nav. (Privacy, Terms, Accessibility, Social media)
Depth: Avoid going more than 3-4 levels deep. If a page requires 5 clicks to reach, most users will not find it.

4.2 Navigation Types & When to Use Them

Navigation TypeStructureBest ForProsCons
Top NavigationHorizontal menu at top showing primary categoriesWebsites with 5-7 main categoriesVisible, always accessible, familiar to usersLimited space; cannot show all options without getting cluttered
Side NavigationVertical menu on left/right showing hierarchyDashboards, content sites, admin panelsShows full hierarchy, can expand/collapseTakes up vertical space on mobile
Footer NavigationLinks in footer organized by categorySecondary/utility content, not primary flowsDoes not clutter primary content areaUsers often miss footer (must scroll all the way down)
Hamburger MenuHidden menu revealed by tap/click on iconMobile apps, responsive sitesSaves space on mobile, clean interfaceNavigation is hidden until user discovers it
Tab NavigationTabs within a section showing options at same levelSwitching between related views (Account, Settings, Notifications)Quick switching, no hierarchyCannot show more than ~5-6 tabs without wrapping
BreadcrumbsShow path from homepage to current pageShowing location in hierarchy, especially on deep pagesHelps user understand where they are, can go backDoes not replace main navigation; secondary cue only
Search-DrivenUsers type to find what they wantLarge products with 1000+ items (Amazon, Google)Fast for users who know what they wantFails if user does not know what to search for; requires good search algorithm

4.3 Navigation Principles

Rules for Good Navigation
Consistent placement: Main navigation in same location on every page. Users should not have to relearn where to look.
Clear labels: "Products" not "Stuff". "Account Settings" not "Config". Use words users understand.
Show current location: Highlight which section/page the user is currently viewing.
Logical grouping: Related categories should be grouped. Do not randomly scatter.
Show hierarchy: Use indentation or nesting to show subcategories are nested under main categories.
Limit primary options: 5-7 main categories max. More than that and users are overwhelmed.
Hide tertiary options: Show primary and secondary in main nav. Tertiary can be shown on the page itself.
Keyboard accessible: Users should navigate via keyboard. Tab through menu items.
Mobile optimized: Navigation must work on small screens. Hamburger menu on mobile, top nav on desktop.

4.4 Labeling & Mental Models

The words you use in navigation are critical. A label can make or break discoverability. The best labels match how users think about the information.

Poor Labels (Designer Thinks)Good Labels (User Thinks)
"Logistics" (what is that?)"Track Order" (I know what this does)
"My Subscriptions" (where do I cancel?)"Billing & Subscriptions" (clear & specific)
"Store Locator" (what is this?)"Find a Store Nearby" (friendly, specific)
"FAQ" (will this help?)"Get Answers" or "Troubleshooting" (action-oriented)
"Transactional History""Order History" (specific & common)
"Settings & Preferences""Account" (simpler)
"Inventory Management""Products" or "Store Inventory" (clear)
"Help Center" (very generic)"Contact Us", "How-To Guides" (specific)

Part 5: Case Study & Full Picture

Duration: 15 minutes

5.1 Real Example: E-Commerce Product Returns Flow

Let us trace the entire IA and flow for a common scenario: a user wants to return a product they bought.

Step 1: IA Structure (Where is Returns?)

Navigation Hierarchy for Returns
User sees top navigation: Products | Deals | Account | Support | About
User clicks "Account" (personal account management)
Submenu shows: Profile | Orders | Returns | Wishlist | Preferences
User clicks "Returns"
Page shows: Active Returns | Return History | How to Return (FAQ)
User clicks "Initiate a Return"

Step 2: User Journey (What does the user feel?)

User started in email notification ("Your order arrived"). They clicked "Return" link. Journey:

SLIDE: User Journey for Returns
Moment 1 - Doubt: "Is this the right product? Should I return it?" → Thinking time
Moment 2 - Anxiety: "How do I even return this? Where do I go?" → Frustration
Moment 3 - Action: Found Account → Returns → "Initiate Return" → Relief
Moment 4 - Clarity: Selects order, confirms return reason → Confident
Moment 5 - Reassurance: "Here is your shipping label, print and drop off" → Happy
Moment 6 - Follow-up: "Your return was received, refund processing" → Satisfied

Step 3: User Flow (What steps does user take?)

The Return Flow
Login → See "Account"
Click "Account" → See "Returns"
Click "Returns" → See "Initiate Return"
Click order from list
Select reason for return (dropdown: Changed mind, Wrong size, Defective, Not as described)
Confirm return condition (New, Like-new, Used)
Review return address
Print shipping label
Pack item and drop off at FedEx
Receive refund confirmation email
Track refund status in Account → Returns → Return History

Step 4: Task Flow (How does "initiate return" work exactly?)

5.2 What Made This IA Good

What Worked Here
Clear navigation: "Account" → "Returns" is logical (returns are part of my account)
Findability: User did not have to search for "returns". One click from menu.
Reduced steps: 3 steps to find returns (Account → Returns → Initiate), not 8
Clear labels: "Initiate Return" not "Return Management" or "RMA Process"
Error prevention: Dropdown for reason (cannot enter random text), condition confirmation (no ambiguity)
Feedback: Confirmation page shows order #, tracking #, estimated refund date
Accessibility: Can access returns from Order History page too (multiple paths)
Mobile optimized: All steps work on small screens, label is printable or sendable

5.3 Connecting Everything: The Full Picture

SLIDE: How IA, Flows, and Design Connect
IA is the blueprint: It structures where "Returns" lives and how it is labeled
User journey is the emotion map: It shows when users are frustrated or delighted
User flows are the navigation paths: They show the big picture (how to return a product)
Task flows are the UI details: They show exactly which buttons to click and forms to fill
Navigation is the signpost: Clear labels and organization mean users find things without getting lost
Screen design executes the flow: Each screen implements one or more steps in the flow
Testing validates everything: Watch real users use the IA. Did they find returns? Did they get lost?
Iteration improves it: If users struggled, reorganize IA, redesign screens, simplify flow, repeat

Session Recap: The Complete Picture

💡 Key Takeaways

Common IA Mistakes to Avoid

What Breaks IA
Organizing by internal structure instead of user goals: "By Department" (Engineering, Sales, Marketing) instead of "By Feature"
Inconsistent labels: "Log in" on homepage, "Sign in" in header, "Authentication" in settings. Pick one term and use it everywhere.
Too many top-level categories: 12 main menu items overwhelm users. Combine into 5-7.
Hiding important information: "Contact us" link only in tiny footer text. Critical info should be discoverable.
Unclear category names: "Resources", "Tools", "Utilities" are vague. Specific names are better.
Deep nesting: Information buried 5+ levels deep. Users cannot find it.
No primary information on the page: User lands on page but has to navigate elsewhere to see primary content.
Conflicting mental models: User expects "Settings" in the main menu but it is hidden under "Admin" → "Configuration".
No search: For large products, search is critical. Do not force browsing through hierarchy.
