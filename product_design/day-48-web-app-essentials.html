Web App Essentials

01 · Introduction to Web Applications

Fig 01 · Netflix-style web app dashboard

A web app runs in the browser, has a backend, stores data, and gives personalised experiences

Unlike a static website, it changes based on who is using it and what they do

Real-World Examples

Netflix — personalised content, watchlists, recommendations per user

Gmail — real-time email, spam filtering, syncs across all devices

Swiggy — location-aware restaurants, live order tracking, payment processing

Amazon — personalised listings, cart, order tracking, seller dashboard

02 · Web App vs Website vs Mobile App

Website

Purpose: inform and showcase content

No login, same content for everyone, minimal data stored

Examples: Wikipedia, portfolio, landing page

Web App

Purpose: perform tasks, complete transactions

Login required, personalised per user, stores data in a database

Examples: Gmail, Figma, Notion, Swiggy

Mobile App

Purpose: mobile-first, on-the-go task completion

Uses device features: camera, GPS, push notifications

Works partially offline, stored on device + server

Examples: Instagram, Uber, WhatsApp

03 · How Modern Digital Products Are Built

💡 Idea — define the problem and who it's for

🔍 Research — user interviews, competitive analysis, personas

🧭 UX — wireframes, user flows, prototypes

🎨 UI — visual design, component library, high-fidelity screens

⚛️ Frontend — turn Figma into HTML, CSS, JavaScript

⚙️ Backend — server logic, business rules, database management

🔌 API — connect frontend and backend, integrate third parties

🧪 QA — test across devices, browsers, and edge cases

🚀 Deploy — publish to a cloud server so real users can access it

👤 Users + Iteration — collect data, find friction, improve, and repeat

Design is one stage in a long pipeline. Understanding what comes before and after your work makes you more effective.

04 · Core Building Blocks

🖥️ Frontend — The UI Layer

Everything the user sees and touches: buttons, forms, text, images

Built with HTML (structure), CSS (styling), JavaScript (interaction)

Responds to user actions and sends requests to the backend

Every component needs: default, hover, active, disabled, and loading states

.btn-primary {

background: #D4500A;

color: white;

border-radius: 8px;

padding: 12px 24px;

}

⚙️ Backend — Logic & Database

Runs on a server — invisible to the user but powers everything

Handles authentication, business rules, payments, and notifications

Reads and writes data to the database

Controls what each user is allowed to see and do

if (user.isLoggedIn) {

showDashboard(user.data);

} else {

redirectTo("/login");

}

🔌 APIs — The Communication Layer

API = contract between frontend and backend — defines how they talk

Frontend sends an HTTP request → backend processes → returns JSON response

GET = fetch data, POST = create, PATCH = update, DELETE = remove

GET /restaurants # list nearby restaurants

GET /restaurants/42/menu # get menu

POST /orders # place an order

POST /auth/login # log in

DELETE /cart/item/7 # remove from cart

05 · How the Internet Works

You type a URL → browser asks DNS to convert it to an IP address

The browser connects to the server and sends an HTTP request

Server processes the request, queries the database, and returns a response

The browser receives HTML + CSS + JS and renders the UI

HTTP Status Codes Designers Must Know

200 OK — success, data returned

301 Redirect — URL has moved

404 Not Found — page or resource does not exist → design a helpful 404 page

500 Server Error — something broke on the server → design a friendly fallback

Every user action is a request. Every result on screen is a response. The milliseconds between them = your UX opportunity.

06 · Key Concepts for Designers

🌐 Hosting, Domains & Databases

Domain — the address of your app (e.g., swiggy.com), costs ~₹800–2000/year

Hosting — the server that runs your app (AWS, Vercel, Netlify)

Database — stores all data: users, orders, products (PostgreSQL, Firebase)

SSL Certificate — the padlock in the browser; without it, the users see "Not Secure.re"

⚡ Performance

Speed is a UX feature — a 1-second delay can drop conversions by 7%

Optimise images — use WebP, set correct dimensions, use lazy loading

Avoid too many fonts and heavy icons — each adds to load time

CDN — serves assets from servers closest to the user globally

Core Web Vitals: FCP (first paint), LCP (largest element), CLS (layout shifts)

Every design decision affects performance. Design with load time in mind from the start.

07 · Types of Web Apps

Static Website

Same HTML served to every user — no personalisation

Fast, cheap to host, no backend needed

Best for: portfolios, docs, landing pages

Dynamic Web App

Content generated per user based on their data and login

Requires backend + database

Best for: dashboards, e-commerce, SaaS tools

Single Page Application (SPA)

One HTML page loads; JavaScript swaps content without full reloads

Feels fast and native — like an app, not a website

Built with React, Vue, or Angular

Loading is per-component, not per-page — design skeleton screens

08 · Role of a Designer

Beyond UI — Think in Systems

Design every state: default, loading, empty, error, partial data

Design for real data — long names, missing images, 0 results, 1000 results

Talk to engineers early — know constraints before you invest design time

Build components, not just screens — think reusability from day one

Own error messages, empty states, loading screens — not just the happy path

Use real content in mockups — lorem ipsum hides UX problems

09 · Common Misconceptions

Fig 09 · Designer myths vs reality

❌ "Designers don't need technical knowledge."

✅ Tech literacy = better decisions, less rework, more trust from engineers

❌ "If it works in Figma, it works in codee.e"

✅ Browsers have constraints — screen sizes, dynamic data, accessibility rules

❌ "UX is just wireframes and flows."

✅ UX = performance, error messages, emails, loading states, 404 pages, all of it

❌ "Loading and error states are the developer's job."

✅ They are prime UX moments — design them with the same care as onboarding

Technical literacy = speaking the language of your medium. You don't need to code — you need to understand.
