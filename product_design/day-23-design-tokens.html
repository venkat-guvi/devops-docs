What is a Design Token?

A design token is a named value — a color, a size, a font weight — that stands in for a hard-coded value everywhere it's used. It's the smallest possible building block of a design system.

💡 Key Insights

Why it matters: Without tokens, the same "blue" gets typed in fifty different files, in fifty slightly different shades.

Real-world analogy: Think of a light switch wired to every lamp in a building. Flip it once, every lamp responds — nobody rewires each lamp by hand.

Product UX perspective: Every rebrand, dark-mode launch, or accessibility fix becomes one edit instead of a hunt through hundreds of screens.

Practical example: color.primary = #2563EB is used by every primary button in the product across all platforms.

Why Tokens are the Core of Design Systems

A design system is built like a building. You can't put up components before you've poured the foundation — and tokens are that foundation.

💡 Key Insights

Why it matters: Components are only as consistent as the values feeding them. Tokens are that feed.

Real-world analogy: A building's foundation isn't glamorous, but every floor above depends on it being level and solid.

Product UX perspective: Teams that skip tokens end up with components that look related but never quite match.

Practical example: A "Card" component doesn't own its own shadow — it borrows elevation.2 from the token layer.

Color Tokens

Color tokens describe purpose , not just hue. "Primary" tells a developer what a color does. "#2563EB" only tells them what it looks like.
💡 Key Insights
Why it matters: Purposeful naming means a designer can swap the entire palette for dark mode without touching a single component.

Real-world analogy: Traffic lights aren't "red, yellow, green" to a driver — they're "stop, caution, go." The name carries the meaning.

Product UX perspective: Danger red should always mean "this is destructive," never just "this happens to be red today."

Practical example: A "Delete account" button always maps to color.danger , on any screen, in any team's file.

Typography Tokens

Typography tokens bundle size, weight, and line-height into one reusable name — so "Heading L" always looks the same, everywhere it's used.

💡 Key Insights

Why it matters: Without a scale, every screen invents its own font sizes — and headings stop feeling like headings.

Real-world analogy: It's like sheet music — a fixed set of notes composers combine, rather than inventing new pitches for every song.

Product UX perspective: A consistent scale builds visual hierarchy users can scan without thinking — they always know what's most important.

Practical example: typography.heading.large bundles 28px / 700 weight / 1.2 line-height into one reusable token.

Spacing Tokens

Almost every mature design system is built on an 8-point grid. Every gap, padding, and margin is a multiple of 8 — so nothing ever looks "almost aligned."

💡 Key Insights

Why it matters: Fixed increments mean any two elements built by different designers will still line up.

Real-world analogy: Think of it like LEGO studs — every piece snaps to the same grid, so anything built separately still fits together.

Product UX perspective: Predictable spacing reduces visual noise, which lowers cognitive load — users read the layout faster.

Practical example: spacing.md = 16px is the default card padding, reused across every card component.

Elevation Tokens

Elevation tokens describe how "high" an element floats above the page — using shadow depth to signal hierarchy, from a flat card to a floating modal.

💡 Key Insights

Why it matters: Elevation tells users what's interactive, what's floating, and what will disappear if they click elsewhere.

Real-world analogy: Like sticky notes stacked on a desk — the ones on top cast a bigger shadow and clearly sit above the rest.

Product UX perspective: A modal needs to feel "above" the page it's blocking — elevation tokens make that instantly readable.

Practical example: elevation.3 is the standard shadow for any dropdown menu across the product.

Token Structure Deep Dive

Tokens exist in three layers, each one built on top of the last: primitive → semantic → component .

💡 Key Insights

Why it matters: Layering lets you change a component's look without touching the underlying brand palette, and vice versa.

Real-world analogy: Raw ingredients → a recipe → a specific dish on the menu. Flour doesn't know it'll become bread.

Product UX perspective: Designers mostly work at the semantic layer — thinking in "primary," not "blue.500."

Practical example: blue.500 → color.primary → button.bg is one value, flowing through all three layers.

Primitive vs Semantic Tokens

This is the single most important distinction in the whole system. Get this right, and everything downstream gets easier.

Blue-500 vs Primary Button Background

💡 Key Insights

Why it matters: If a component referenced blue.500 directly, renaming the brand's blue would break every button.

Real-world analogy: A phone number vs. a contact name. "Mom" always resolves to the right number, even if the number changes.

Product UX perspective: Designers pick from semantic tokens in their tool — they never need to know the raw hex value underneath.

Practical example: A dark-mode theme simply repoints color.primary to a different primitive, no component code changes.

Token Naming Conventions

A good name tells you what a token does before you ever see its value. Names should read like a sentence: category → property → variant.

Scalable Naming Systems

Good Naming vs Bad Naming

💡 Key Insights

Why it matters: "TestColor" surviving into production is how design systems quietly rot from the inside.

Real-world analogy: Good naming is a well-organized filing cabinet — you find "tax documents 2024" without opening every drawer.

Product UX perspective: New designers should be able to guess a token's name correctly before they even open the library.

Practical example: button.primary.bg.hover instantly tells you the component, state, and property.

The Design → Development Bridge

How Developers Consume Tokens

💡 Key Insights

Why it matters: Removing manual hand-off eliminates the classic "that's not the blue I designed" bug report.

Real-world analogy: It's a translator that speaks both "designer" and "engineer" fluently, with zero information lost.

Product UX perspective: Designers can trust that what they see in Figma is what genuinely ships — no translation drift.

Practical example: A Figma variable named spacing.md becomes --spacing-md in CSS automatically.

Mapping Tokens to Components

Take any component apart, and every visual property traces back to a token. Nothing is left to guesswork.

💡 Key Insights

Why it matters: Mapping makes components predictable — swap a token, and only that one property visibly changes.

Real-world analogy: Like a car's parts diagram — every bolt has a part number you can order and replace on its own.

Product UX perspective: QA can verify a component visually just by checking which tokens it references — no eyeballing hex codes.

Practical example: A "Danger" button variant just swaps color.primary for color.danger — nothing else changes.

Why it matters: Consistency isn't a one-time achievement — it has to be maintained as the product keeps growing.

Real-world analogy: Like tending a garden — a system left unattended slowly grows weeds, even if it started out clean.

Product UX perspective: Partial adoption is often worse than no tokens — teams assume consistency that doesn't fully exist yet.

Practical example: A linter that flags any hard-coded hex value in code review keeps the system honest over time.

Common Challenges in Token Systems

Every mature system runs into the same handful of problems. Knowing them ahead of time means you can design around them.

💡 Key Insights

Why it matters: Recognizing these patterns early is far cheaper than untangling them after hundreds of screens exist.

Real-world analogy: It's like technical debt in code — invisible at first, expensive to pay down once it's everywhere.

Product UX perspective: A confusing token library slows designers down more than having no system at all.

Practical example: A quarterly token audit that deprecates anything unused for 90+ days keeps the library lean.
