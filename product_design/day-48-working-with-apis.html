What is an API?

API = Application Programming Interface — a messenger between two software systems

User sends a request → API carries it → App responds

Every tap, swipe, and search in any dynamic app triggers at least one API call

The restaurant analogy

You are the user. The waiter is the API. The kitchen is the server. You never enter the kitchen — you just get your dish. APIs work the same way.

Why designers should care

All UI data (prices, names, orders, feeds) comes from APIs — nothing is hardcoded.

Understanding APIs helps you design buildable, realistic UIs

Developers will trust and respect your specs far more when you speak their language

UX INSIGHT When you know how APIs work, your designs become engineering-aware — you stop designing utopian UIs and start designing real, buildable ones.

02 · How APIs Work

The Request → Response cycle

Every API interaction follows one pattern: Request → Server processes → Response.

Step 1: User action triggers a request (e.g., tap "Search Restaurants")

Step 2: App fires the API request (GET /restaurants?city=Chennai)

Step 3: Server receives it, queries the database

Step 4: Server sends back a response (JSON list of restaurants)

Step 5: App renders the data on screen — user sees results

The cab booking analogy

You open Ola and tap "Book Ride" (request). Ola checks for nearby drivers (server lookup). It sends back driver info (response). Your screen updates — all in under a second. That speed? APIs are doing their job perfectly.

UX INSIGHT The time between request and response is when your loading state, skeleton screen, or spinner appears. Designing this in-between moment well separates average apps from great ones.

03 · Real-world Examples

a) Payment systems (GPay, Razorpay)

At least 4 APIs fire in sequence when you pay on Amazon

Flow: User taps Pay → App → Payment Gateway API → Bank API → Success response

As a designer: plan timeout screens, failure screens, and retry CTAs for each step

b) Login & authentication

POST /login sends credentials → Server verifies → Token returned to app

Every future API call carries this token — it proves the user is authenticated

Design: loading state while verifying, clear error for wrong password, success redirect

c) Data fetching (Instagram / Flipkart)

Every scroll loads a new batch of posts via API — called pagination

App fetches 10-20 posts at a time, triggered by scroll position

This directly impacts your infinite scroll UX, loading indicator placement, and end-of-feed messaging

UX INSIGHT GPay's retry screen and Instagram's skeleton loader are not afterthoughts — they are deliberate UX decisions based on how APIs behave. You must design for them, too.

04 · Types of APIs

REST APIs — the industry standard

REST = Representational State Transfer — the default API style in 90% of products

Uses standard HTTP verbs to perform actions on data (users, orders, products)

GET — reads/fetches data (load Flipkart search results)

POST — creates new data (place an order, log in)

PUT — updates existing data (edit delivery address)

DELETE — removes data (cancel order, delete cart item)

What endpoints look like

GET /products → Load product listing page

GET /products/42 → Load a single product

POST /login → Log in (send email + password)

POST /cart/items → Add item to cart

DELETE /cart/items/7 → Remove item from cart

💡 UX INSIGHT Each endpoint returns specific fields. If you design UI elements that need data the API does not provide, you create an engineering conflict that delays the project every time.

05 · API in Product Design

Designing with dynamic data

Static UI = hardcoded, fixed content (like a poster)

Dynamic UI = data fetched from APIs, unique for every user

Every UI element must map to a real field in the API response — or it will not render

Conversely, every API field must have a corresponding UI element — or it is wasted data

The three states every screen must have

Loading state — skeleton screens while API call is in flight (never blank pages)

Success state — happy path with real data rendered correctly

Error state — clear error message + a recovery action (Retry, Go Back)

A handoff missing two of these three states is an incomplete design.

Sample API response

{
"name": "Priya Sharma",
"orders": 3,
"status": "active",
"lastOrder": "Biryani from Meghana Foods",
"loyaltyPoints": 420
}
UX INSIGHT Skeleton loaders (animated gray placeholders) reduce perceived loading time by 20-30%. They are trivially easy to design but have an outsized impact on user satisfaction.

06 · Common API Concepts

Endpoints

An endpoint is a specific URL where an API lives — like a door to a data room

/products → product list (name, price, image, stock)

/orders → order history (status, date, items)

/users/me → logged-in user profile

/cart → current cart items, quantities, and total

JSON data

JSON = JavaScript Object Notation — the format in which API responses return data

Looks like a structured list of labels (keys) and values

You do not write it — but you must be able to read it

Sample product JSON

{
"product": "Nike Air Max",
"price": 2999,
"stock": true,
"rating": 4.3,
"badge": "Best Seller",
"sizes": [7,8,9,10]
}

badge → "Best Seller" chip on card | sizes → size selector buttons | stock: false → disabled "Add to Cart" button

UX INSIGHT In design reviews, senior designers ask: "Where does this data come from?" Answering "it comes from the product field in the /products endpoint" earns instant credibility with engineers and PMs.

07 · Limitations Designers Should Know

Latency

Latency = time between the request sent and the response received

Even on fast internet: 100–500ms round trip

On slow networks: 2–3 seconds — always design for this

0–200ms: instant, no loader needed

200ms–1s: show skeleton loader

1s+: show progress indicator + timeout message

Error handling

APIs fail — servers go down, networks drop — design for it

400: Bad request (app sent wrong data)

401: Unauthorized (user not logged in)

404: Not found (product/page does not exist)

500: Server error (backend problem)

Sample error response

{
"status": 500,
"error": "Server not responding",
"message": "Unable to fetch restaurants. Try again."
}

Three UX patterns for failures

Skeleton loaders — animated placeholders that mirror the expected layout

Retry states — clear error message + one-tap "Try again" action

Offline UX — show cached data or a helpful offline screen — never strand users

UX INSIGHT "Couldn't load restaurants. Check your connection and try again →" beats "Error 500" every single time. You control the message — make it human and actionable.

08 · Common Mistakes

Designing without real data

Using "Lorem ipsum" or "John Doe" creates designs that break when real data arrives.

Names that are 2 words or 40 characters, prices of ₹4 or ₹40,000, products with no image

Always design with realistic data from the very first frame

Ignoring edge cases

What if the order list is empty? → Empty state must be designed

What if the username is 80 characters? → Text truncation and overflow must be handled

What if the product has zero reviews? → Null values must not crash the UI

Only designing successful states

Handing off only the happy path is like designing only the front door of a building.

Loading + error states are not optional — they are part of the design

Designing data that does not exist in the API

Adding a "Last Active" badge that does not exist in the API forces devs to build a new endpoint

Always ask: "Does the API already return this field?" before designing any element.

💡 UX INSIGHT Before handoff, stress-test your own design: What breaks if the name is 100 characters? If there are 0 items? If the image URL returns a 404? These questions are API-thinking, and they make your work production-ready.

09 · How Apps Use APIs in Real Scenarios

Food delivery (Swiggy / Zomato)

GET /restaurants → Search results page (restaurants near you)

GET /menu/:id → Restaurant detail page (menu, prices)

POST /cart → Add items to cart

POST /payment → Process payment

GET /order/:id/track → Live order tracking screen

E-commerce (Amazon / Flipkart)

GET /products?q=shoes → Search results

GET /products/42 → Product detail page

POST /cart/items → Add to cart

POST /checkout → Initiate checkout flow

POST /payment → Process payment → Order confirmation

Social media (Instagram / X)

POST /login → Authentication, token returned

GET /feed?page=1 → Load initial feed

POST /likes/:postId → Like a post

POST /comments → Add a comment

GET /feed?page=2 → Load more as user scrolls

💡 UX INSIGHT The best designers ask in sprint planning: "What APIs do we have available for this feature?" API availability determines feature feasibility — knowing this saves weeks of rework.
