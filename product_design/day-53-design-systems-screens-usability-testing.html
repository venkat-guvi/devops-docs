Part 1: From Idea to Design Systems

1.1 From Idea to Actual Product

Every product starts as a concept: a problem to solve, a need to meet. But concept ≠ product. The leap from "I have an idea for an app" to "people are using my app daily" requires a structured design process.

SLIDE: The Concept-to-Product Journey
Concept: "We should help users manage their time better"
Research: Talk to users about their current struggles. Define the real problem.
Product: Define scope. What specific problem are we solving? What is out of scope?
Design System: Define the visual language, components, and patterns that will scale this product
Screens: Design the actual user interface for the core flows
Prototype: Build an interactive mockup to test interactions
Testing: Watch real users try to use it. Does it work? What breaks?
Iteration: Fix what breaks. Improve what works. Repeat.
Launch: Release to users and continue iterating based on real usage data

1.2 Why Design Systems Matter (Even Small Products)

A design system is a centralized source of truth for how a product looks and behaves. It includes colours, typography, spacing, components, and patterns. You might think: "My product is small, why do I need a system?" The answer: because the system is how you stay consistent as you grow.

What a Design System Is NOT
NOT a Figma file (a Figma file holds the system, but it is not the system)
NOT just a colour palette (colour is one layer)
NOT a checklist you follow robotically (it is a source of truth, not a straightjacket)
NOT something built once and never changed (systems evolve with products)
What a Design System DOES:
Defines core building blocks: colours, typography, spacing grid, components (buttons, inputs, cards)
Ensures consistency across all screens: the same button looks and behaves the same everywhere
Speeds up design: designers do not reinvent the wheel for every screen
Enables handoff to code: engineers build components once, reuse them everywhere
Makes maintenance possible: change a colour in the system, it updates every instance
Allows the team to scale: new designers and engineers can use the system immediately
Documents decisions: "Why is this spacing 16px not 12px?" The system explains

1.3 Core Elements: Recap Connection to Components

Remember from Components & Variants session? Everything connects. A design system is built on these layers:

LayerWhat It IsWhy It MattersExamples

Part 2: Designing Visual Screens

2.1 Applying Hierarchy, Layout, and Consistency

A screen is where the system meets reality. It is where users see and interact with your product. Good screen design applies three principles: visual hierarchy (what is important?), layout (where do things go?), and consistency (does this follow our system?).

Visual Hierarchy

Visual Hierarchy: Making Importance Visible
Size: Most important element is largest. Your CTA button is 48px, secondary buttons are 36px.
Colour: Primary actions use your brand colour. Secondary actions use neutral. Destructive actions use red.
Weight: Bold text for headings and labels. Regular weight for body copy.
Spacing: Important items have more breathing room (negative space). Unimportant items are tucked away.
Contrast: High-contrast elements (white on dark) stand out. Low-contrast elements recede.
Position: Users scan top-left first (in LTR languages). Put primary CTA above the fold.

Layout Systems

Most digital products use a grid-based layout. A common grid is 12 columns × 8px base unit. Components and content snap to this grid. This creates rhythm and alignment that the eye finds satisfying.

Single-Column LayoutMulti-Column Layout
Entire content flows in one column (common on mobile)Content spans multiple columns (common on desktop)
Predictable left-to-right reading orderMain content in left column, sidebar on right
Easy to read on any screen widthFlexible. Can show multiple sections at once.
Limited design flexibilityRequires careful alignment or it looks chaotic
Example: Blog posts, email, mobile appsExample: Dashboards, product pages, settings

2.2 Maintaining Usability While Designing

A beautiful screen that confuses users is a failed screen. Usability means: can a user accomplish their goal without friction? Keep these principles in mind:

Usability Principles While Designing Screens
Clarity: Every element has a clear purpose. Users should not have to guess what a button does.
Feedback: When users take an action (click, submit), give them feedback. A loading spinner, success message, or error message.
Consistency: If you implemented a pattern on Screen A (e.g. form validation), use the same pattern on Screen B.
Contrast: Text must be readable. WCAG AA minimum: 4.5:1 contrast ratio for body text, 3:1 for large text.
Scan-ability: Users scan, not read. Headings, white space, and short paragraphs help users find what they need.
Affordance: Visual design should suggest interaction. Buttons look clickable, inputs look typable, links look clickable.
Minimize cognitive load: Do not make users remember information or count steps. Errors should prevent bad data, not punish users for making mistakes.

Part 3: Prototyping & User Flows

3.1 What is Prototyping?

A prototype is a representation of your design. It is not final code. It is not the shipping product. It is a tool for thinking through interactions, testing assumptions, and getting feedback early.

3.2 Prototyping Spectrum: Low to High Fidelity

3.3 User Flows: How Users Move Through Products

A user flow shows the path a person takes to accomplish a goal. It maps steps, decisions, and interactions. Flows help you understand: how many steps are required? Where might users get stuck? Where can we shortcut the path?

SLIDE: Anatomy of a User Flow
Start state: Where does the user begin? (logged in? on homepage?)
Steps: Each action the user takes (click button, fill form, submit)
Decisions: "Does the form validate?" If yes, go to next step. If no, show error.
End state: Where does the user end up? Did they accomplish their goal?
Alternatives: What if something fails? What if the user changes their mind?
Emotional layer: Where might the user get frustrated? Where might they abandon?

Part 4: Usability Testing

4.1 What is Usability Testing & Why It Matters

Usability testing is watching a real user try to use your design. You give them a goal ("Add an item to your cart") and you watch them attempt it. You do not help them. You do not answer questions. You observe: can they do it? What confuses them? What breaks?

"The best person to tell you what is wrong with your design is not your boss or a senior designer. It is a real user who has never seen it before." — Steve Krug
Why Usability Testing Matters
You are not the user. Your assumptions about what is "obvious" are often wrong.
Early testing saves costly revisions. Finding issues in a prototype is infinitely cheaper than finding them after launch.
Users reveal edge cases designers never considered (e.g., "What if I want to edit an order after placing it?")
Quantifies the problem. Instead of debating whether a button is confusing, you see 7 out of 10 users miss it.
Provides directional feedback for iteration. "Dark mode" is vague. "I did not see this button because it blended into the background" is actionable.

4.2 Types of Usability Testing

4.3 Best Practices for Conducting Tests

How to Run a Usability Test (The Right Way)
Recruit the right people: Test with people who match your target user. Do not test with colleagues (they know the product too well).
Write a scenario, not a task: Instead of "Add item to cart", say "You need to buy a birthday gift for your friend. Use this website." This gives context.
Give one task at a time: Do not overwhelm users with 10 tasks. 3-5 focused tasks per session.
Do not help or hints: If a user is lost, let them be lost. That is data. If you explain or hint, you are no longer testing the design.
Ask "why": When a user hesitates or makes a mistake, ask "Why did you try that?" or "What were you looking for?"
Record with permission: Take notes and record video (if participant consents). Review recordings to spot patterns you missed in real-time.
Debrief after: After the test, ask open-ended questions: "What was your overall impression?" "Anything confusing?"
Analyze: Look for patterns. If 6 out of 8 users got stuck on the same step, that is a usability issue to fix.

Part 5: What to Observe in Testing

5.1 User Behavior vs User Feedback

User Behavior (What They Do)User Feedback (What They Say)
The user hovers over an element 5 times before clicking"This button is confusing"
The user skips filling a "middle name" field"I do not know what to fill in this field"
The user closes the modal after 10 seconds"That modal does not give me enough information"
The user tries clicking on text that looks like a button but is not"I thought that was clickable"
The user enters their birthday in the email field (misunderstood the field)"I did not realize this was a separate field"

Behavior is truth. Feedback is interpretation. When a user says "This is confusing" but completes the task quickly and confidently, the design is probably fine. When a user says "This is easy" but spends 3 minutes trying to find a button, the design is broken.

5.2 Common Usability Issues

IssueWhat It Looks LikeRoot CauseHow to Fix
ConfusionUser does not understand what the page is about. What should they do?Unclear headline, unclear value proposition, too much textWrite a clear headline (what is this page about in <5 words?). Show primary CTA.
FrictionUser has to take too many steps to accomplish goal. Feels annoying.Form too long, too many questions, unclear stepsReduce form fields. Show progress. Autofill when possible.
Cognitive OverloadUser sees too much information at once. Paralysed by options.Too many buttons, too many options, no hierarchyReduce options. Simplify hierarchy. Hide advanced options.
Unexpected BehaviorUser clicks something expecting outcome A, gets outcome BPoor affordance (it does not look clickable), unclear labelMake interactive elements look interactive. Write clear labels.
Hidden ContentUser does not see important information because it is scrolled away or behind a menuPoor layout, poor placementPut critical info above the fold. Do not hide behind accordions on mobile.
Data LossUser fills a form, steps away, comes back, and all data is goneNo autosave, form did not saveAutosave drafts. Warn before leaving with unsaved data.
Error MysteryUser submits form, gets a generic error. Does not know what to fix.Poor error messaging. No indication of what went wrong.Inline validation. Field-level error messages. Explain how to fix.

Part 6: Iteration & Complete Design Lifecycle

6.1 Why Design is Never Final

You design → you test → you find issues → you iterate. This is not a linear process that ends. Every release brings new data from real users. Good design is a cycle of continuous improvement, not a single perfect version.

SLIDE: The Iteration Cycle
Design: Create screens based on user research, best practices, and system constraints
Prototype: Build an interactive version to test interactions and flows
Test: Watch 5-8 users try to use it. Observe behavior. Take notes.
Analyze: Look for patterns. What worked? What broke?
Iterate: Fix the broken things. Refine the things that almost worked.
Launch: Release to users (full or gradual rollout)
Measure: Track metrics (engagement, retention, conversion, errors) in production
Loop: What did real users do with it? Any surprises? Any new problems? Start back at Design.

6.2 Analyzing a Product Flow: What Works, What Fails

Let us analyze a real example: a checkout flow. Every step, every element, every interaction is an opportunity to either help or confuse a user.

From this analysis, the priorities for iteration are: 1) Explain "Address Line 2" with placeholder text. 2) Move "I agree to terms" above the fold and make it more prominent. 3) Clarify delivery dates (show calendar or "arrives by" date). 4) Add post-order messaging (estimated arrival, tracking link).

6.3 The Complete Product Design Lifecycle

Everything connects. Here is how all the pieces fit together in a real product cycle:

The Full Lifecycle (Simplified)
1. CONCEPT + RESEARCH: Define the problem. Interview 10 users. Build a persona.
2. DESIGN SYSTEM: Define colours, typography, spacing, core components before designing screens.
3. FLOWS + WIREFRAMES: Map the happy path. Draw wireframes of key screens.
4. DESIGN SCREENS: Apply hierarchy, layout, consistency using the system.
5. PROTOTYPE: Make it interactive. Test a button click flow.
6. USABILITY TEST: Recruit 5-8 users. Give them a task. Watch them struggle and succeed.
7. ANALYZE + ITERATE: Fix the bugs. Refine the rough edges.
8. FINAL DESIGN: Polish, get stakeholder sign-off.
9. HANDOFF: Pass designs to engineering with component specs.
10. BUILD: Engineers build the product using the design system components.
11. LAUNCH: Release to users (often a gradual rollout, not all-at-once).
12. MEASURE: Track metrics in production. Did the design meet goals?
13. GATHER FEEDBACK: Users provide real-world data. Analytics show actual behavior.
14. LOOP: Back to step 1 for the next feature or improvement cycle.
