MODULE 1 — Collaboration Foundation

01 Introduction to Design–Development Collaboration

📌
02 / 31

1. What is it?

Design–Dev collaboration is a continuous workflow where designers and developers work together throughout the product lifecycle — not in isolated stages.

Flow: Design → Handoff → Development → QA → Feedback → Iterate

📌
03 / 31

2. Why it matters

When collaboration is missing:

Designs get misinterpreted

UI inconsistencies appear

Rework increases

Delivery slows down

Strong collaboration keeps the product aligned from design to launch and reduces unnecessary back-and-forth.

📌
04 / 31

3. Key understanding

Design does not end in Figma — it continues until release

Developers rely on structured specifications, not just visuals

Early developer involvement prevents late-stage confusion

📌
05 / 31

4. How collaboration happens in practice

Designers share clean, structured files

Developers are involved early in discussions

Teams use shared systems (design tokens, components)

Feedback loops exist across all stages

Supporting tools:

Figma (design + inspect)

Zeplin (handoff clarity)

Storybook (component library)

Jira (task tracking)

02 Why Most Design–Dev Handoffs Fail

📌
06 / 31

1. What actually goes wrong ?

The handoff stage is where collaboration most often breaks.

Designers usually hand over a visually complete screen, but developers receive something incomplete for implementation.

The gap looks like this:

No interaction states

No exact spacing values

No design tokens (colors, typography, etc.)

Because of this, developers are forced to guess — and guessing leads to inconsistencies.

📌
07 / 31

2. Why does this become a problem ?

A design might look perfect, but without clarity:

UI gets implemented differently

Small inconsistencies multiply across screens

Teams waste time clarifying basic things

Rework becomes unavoidable

📌
08 / 31

3. What typically breaks handoffs ?

Ambiguous specifications Instead of clear values, vague instructions are given → “slightly darker hover” instead of a hex code

Missing states Only default UI is designed → hover, active, error, loading states are missing

No shared language Component names in design don’t match code → confusion between design and development

One-way delivery Design is just handed off without discussion → no walkthrough, no alignment

03 Difference in Thinking: Designer vs Developer

03 Difference in Thinking: Designer vs Developer

Two Different Lenses

📌
09 / 31

1. The core idea

Designers and developers approach the same product from two very different perspectives.

Designers focus on how it looks and feels → aesthetics, emotion, user flow

Developers focus on how it works and scales → logic, structure, reusability

Neither side is wrong — they’re solving different parts of the same problem. Friction starts when these perspectives don’t align.

📌
10 / 31

2. Where does the gap show up ?

Vague vs precise communication

“This card should feel premium” → Developer: What does that mean technically?

“Use a slightly darker hover” → Developer: Give me the exact hex value

Different thinking models

Designer → thinks in screens and flows

Developer → thinks in components and states

This difference is natural — but without alignment, it creates confusion.

📌
11 / 31

3. How do teams bridge this gap ?

Good teams don’t force one side to change — they create a shared language.

That includes:

Design tokens (colors, spacing, typography)

Clear annotations (what exactly should happen)

Consistent naming (same terms in design and code)

This turns subjective ideas into something developers can build accurately.

04 How Developers Read Designs

Spec-First Mindset

📌
12 / 31

1. The core idea

Developers don’t open design files for inspiration — They open them to extract exact specifications.

To a developer, a Figma file is not just a visual — It's a technical contract.

If something isn’t clearly defined, it won’t be guessed correctly — it will be estimated, and estimates often lead to inconsistencies.

📌
13 / 31

2. How developers actually read designs

When developers inspect a screen, they’re scanning for precise values:

What is the exact color?

What is the spacing on each side?

What font and weight is used?

What component is this mapped to?

What happens in different states?

They are translating design into code-ready details, not interpreting intent.

📌
14 / 31

3. What developers look for first

Colors Exact hex codes or token names → not “light purple”

Spacing Padding and margin values → top, right, bottom, left clearly defined

Typography Font family, size, weight, and line-height

Component naming Should match existing code components → avoids duplication and confusion

States All variations must be defined: → default, hover, focus, disabled, error

📌
15 / 31

4. Why this matters

When specs are missing:

Developers make assumptions

UI inconsistencies appear

Time is wasted in back-and-forth discussions

Design intent gets diluted

Clear specs = faster development + accurate output

05 Understanding Specs, Spacing & Tokens

Design Tokens

📌
16 / 31

1. What are design tokens?

Design tokens are named variables that store design decisions like colors, spacing, and typography — and are shared between design and development.

Instead of hardcoding values like #4f3ef5, teams use meaningful names like: → --brand-primary

This creates a single source of truth across Figma and code.

📌
17 / 31

2. Why does this change everything ?

Without tokens, teams constantly ask: → “Which blue should I use?”

With tokens:

That question disappears

Changes happen in one place

Updates reflect everywhere automatically

Imagine a rebrand:

Without tokens → manual updates across hundreds of screens

With tokens → update one value → everything updates instantly

This saves huge amounts of time and effort

📌
18 / 31

3. Key concepts to understand

Consistent spacing system Use a structured scale like: → 4, 8, 12, 16, 24, 32… This keeps layouts consistent and predictable

Named typography system Avoid raw pixel values like “14px” Use meaningful names like: → text-sm, text-body, text-h2

Figma Variables → Code connection With Figma Variables (2023+), design values can directly map to: → CSS custom properties (tokens in code)

This creates a seamless bridge between design and development

Industry-standard systems Well-known systems like:

Material Design

Shopify Polaris

are fully built using design tokens

06 What Developers Actually Need vs What Designers Give

📌

A beautiful default state Figma file

One breakpoint (desktop only)

Unlabeled components

No interaction or micro-animation notes

📌

WHAT DEVELOPERS ACTUALLY NEED

All states: default, hover, focus, error, loading, empty

All breakpoints: mobile, tablet, desktop

Component names that match code

Interaction notes: "slide in from bottom on tap"

Edge cases: long text, empty cart, slow loading

📌
21 / 31

THE HANDOFF CHECKLIST

Figma → Inspect: all layers named, tokens applied, auto-layout used.

Specs sheet: typography, spacing, color tokens documented on a separate page.

Component library: published and linked in the dev file.

Prototype link: shows interactions and transitions.

Handoff notes: short comment on each tricky section in Figma.

07 Common Handoff Mistakes

📌
22 / 31

MISTAKES THAT HURT MOST

Missing states:

no hover, focus, active, disabled, loading, or error. Dev guesses — always wrong.

Inconsistent spacing:

15px here, 17px there — not on any grid. Developers hate this.

Unlinked components:

Every button is a unique shape instead of a shared library item.

No edge case design:

Long names, empty lists, zero results, API errors — all undesigned.

Wrong export scale:

1x PNG instead of 2x or SVG causes blurry assets in production.

MODULE 3 — Speaking Dev Language & Documentation

08 Speaking Developer Language

📌
23 / 31

CORE CONCEPTS

px → rem: base 16px = 1rem. rem scales with the user's browser font size — it's accessible by default.

Naming: btn-primary not Button_blue; card-product not CardV2_FINAL.

Token vars: color: var(--brand-primary) not #4f3ef5. One variable, infinite reach.

CSS Box Model: margin (outside), padding (inside), border-radius, z-index — know these colds.

09 Design System Documentation

Design system documentation is the written rulebook for using components — when to use them, how to use them, and what to avoid.

It lives alongside the components in Figma or Storybook.

Without docs, every team interprets the system differently. With docs, new designers and devs onboard in hours, not weeks.

📌
24 / 31

WHAT GOOD DOCUMENTATION INCLUDES

Component purpose:

One line explaining what this component does and when to use it.

All variants:

Primary, secondary, ghost, danger, loading, disabled — all shown visually.

Props/anatomy:

Label, icon, size, variant, disabled — all named and explained.

Do/Don't examples:

Show the right usage next to the wrong one. Visual = instant understanding.

Accessibility notes:

keyboard focus, ARIA labels, contrast ratio.

MODULE 4 — System Thinking & Design Systems

10 System Thinking

10 System Thinking

📌
25 / 31

.HOW TO THINK SYSTEMICALLY

Design flows, not screens — always ask "what happens before and after this screen?"

Shared components everywhere: same navbar, footer, button, toast — all from one library.

Consistent patterns: if cards open a drawer on Screen 2, they should open a drawer everywhere.

Error states as a system: one error component style used across all forms.

Amazon has 400+ screens and one design language — every button, icon, and spacing follows the same system.

11 Scaling Design Systems

Scaling a design system means growing one core system to support multiple teams and platforms — while keeping everything consistent and reliable.

One shared system powers web, mobile, and other teams using the same tokens and components.

📌
26 / 31

HOW SCALING WORKS

Versioning: like software — v1.0, v1.1, v2.0. Breaking changes = major version bump.

Contribution model: teams propose new components that go through review before entering core.

Sub-systems: Mobile inherits from core but adds platform-specific patterns (bottom sheet, swipe).

Governance team: a dedicated design system squad owns the library — not everyone's side project.

MODULE 5 — Real Challenges, Maintenance & Future

12 Real-World Challenges

📌
27 / 31

THE 3 MOST COMMON REAL PROBLEMS

Over-engineered: a startup with 10 screens builds 300 components. No one can maintain it. Start small, grow slow.

Under-defined: no naming rules, no docs, no governance. The system exists on paper only.

Adoption issues: developers skip the design system and build custom components because "it's faster." Result: 4 different button styles in production.

📌
28 / 31

HOW TO FIX EACH

Over-engineered → start with 10 core components. Grow based on real demand.

Under-defined → write one page of rules per component. Even a Notion page counts.

Adoption → make the system easier to use than building custom. Ship Storybook, write examples, host office hours.

13 Maintaining a Design System

13 Maintaining a Design System

📌
29 / 31

MAINTENANCE HABITS THAT WORK

Monthly audit: check for inconsistencies between Figma library and production code.

Changelog: document every change — what changed, why, and how to migrate.

Deprecation policy: never delete — mark as deprecated, keep for 2 versions.

Office hours: weekly 30-min session where teams can ask design system questions.

Feedback loop: a Slack channel (#design-system) where teams report issues and request additions.

14 Future of Design Systems

📌
30 / 31

WHAT'S COMING (ALREADY PARTLY HERE)

AI-generated UI: tools like v0.dev, Figma AI, Copilot generate components from a prompt — using your own design system.

Figma Variables → CSS: one token change in Figma pushes to code via GitHub Actions. Fully automated.

Multi-theme systems: one system, swap brand colors with a JSON file. A/B themes, white-label, dark mode — all automatic.

Visual regression testing: tools like Chromatic auto-screenshot every component on every PR. Catches design drift before it ships.

Designers as engineers: the line blurs further — design system teams write code, not just Figma files.

📌
31 / 31

WHAT THIS MEANS FOR YOU

Learn tokens deeply — they're the bridge between design and code.

Know at least one design system well: Material, Polaris, Atlaskit.

Understand versioning, documentation, and governance — not just visual design.

Get comfortable with basic HTML/CSS. You don't need to be a dev. You need to speak their language.

3 Things to Remember

Design for Develop - Every design decision has a build cost. Make specs clear. Use tokens. Design all states.

Think in Systems — Don't design screens in isolation. Design components, flows, and rules that scale.

Document Everything — If it's not written down, it doesn't exist. Rules, tokens, usage guidelines — all must be documented.
