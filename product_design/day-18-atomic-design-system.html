Part 1: Introduction to Atomic Design

What is Atomic Design?

Atomic Design is not a tool, a plugin, or a Figma feature. It is a mental model — a way of thinking about UI structure. The tool you use (Figma, Sketch, code) is secondary. The thinking comes first.

The Problem Atomic Design Solves

Before design systems and atomic thinking became standard practice, most product teams designed screen by screen. Every designer made individual decisions about spacing, colour, button size, and typography — on every screen, every time. The results were predictable:

What Changes When You Think Atomically

Designing ScreensDesigning a System
Each screen is a unique artifactEach screen is an assembly of reusable parts
Change one screen, update only that screenChange one atom, update every screen instantly
New screen requires design from scratchNew screen requires composition of existing pieces
Inconsistency is the default outcomeConsistency is the automatic outcome
Design and dev share screens as the specDesign and dev share components as the spec
A component library is 'nice to have'A component library is the primary deliverable
The goal is beautiful screensThe goal is a consistent, scalable system

All Five Levels at a Glance

LevelDefinitionExamples
ATOMSThe smallest possible UI elements. They cannot be broken down further without losing their function.Buttons, input fields, labels, icons, colour swatches, typography styles, spacing tokens, dividers
MOLECULESSimple groups of atoms functioning together as a unit. Each molecule has one clear, focused purpose.Search bar (input + button + icon), form field (label + input + error text), card thumbnail (image + label)
ORGANISMSRelatively complex components built from groups of molecules and atoms. They form distinct sections of UI.Navigation bar, product card grid, hero section, comment thread, pricing table, checkout form
TEMPLATESPage-level skeletons that place organisms into a layout. No real content — only structure and wireframe.Article page layout, dashboard shell, e-commerce product page grid, settings page structure
PAGESTemplates filled with real content. This is what the end user actually sees and interacts with.Live homepage, actual product detail page, real user dashboard with data and media

Why Zomato ?

Zomato's home screen is an ideal teaching example because it contains every atomic level in a single view — atoms, molecules, organisms, and a clear template structure — and every student is familiar with it. The same analysis applies equally to Swiggy, Flipkart, Amazon, or any product you choose to substitute.

Part 5: Component Thinking — Building from Small to Large

What is Component Thinking?

Component thinking is the mental practice of seeing every interface element as a building block that should be defined, named, documented, and reused — rather than drawn freshly each time it appears. It is the design equivalent of a developer thinking in functions and classes.

A designer who thinks in components asks these questions before adding any element to a screen:

Does this component already exist in the system?

If not, is this a new atom, molecule, or organism that should be added to the system?

If it is a variant of an existing component, can I solve this with a new variant rather than a new component?

If this is truly unique to this screen, should it become a component for future use?

Variants and Properties in Figma

In Figma, an atom is not just one component — it is a component with variants covering every state, size, and type it can appear in.

Button Component — Variant Structure

Property: Type → Primary | Secondary | Ghost | Destructive | Link

Property: Size → Large | Medium | Small

Property: State → Default | Hover | Pressed | Disabled | Loading

Property: Icon → None | Left | Right | Only

One Button component with these four properties generates 5 × 3 × 5 × 4 = 300 possible combinations — all from a single master component.

Input Field Component — Variant Structure

Property: Type → Text | Password | Search | Number | Textarea

Property: State → Empty | Focused | Filled | Error | Disabled

Property: Size → Large | Medium | Small

Property: Label → With Label | Without Label

Part 7: Scalability & Reusability

Scalability

Scalability means the system can grow — in screens, features, products, and team size — without proportional growth in design effort or without degradation in visual consistency.

Reusability

Reusability means a component built once is used everywhere it is needed, without modification. True reusability requires components to be designed with flexibility — through props, variants, and slots — rather than designed for a single context.

Part 9: Common Mistakes & Designing Screens vs Systems

Designing Screens Instead of Systems — The Root Mistake

Signs that a designer is designing screens instead of a system:

Every screen has its own version of a button with slightly different properties

There is no component library — only a collection of designed screens

Changing the CTA button colour requires opening every screen file manually

A new designer on the team cannot find a 'standard' for anything — because there isn't one

The design handoff to developers is a PDF of screens, not a component specification

The fix is not to retroactively extract components from existing screens. The fix is to change the starting point — begin every design project by defining atoms, building molecules, composing organisms, and only then assembling screens.

Key Principles to Carry Forward

Build systems, not screensScreens are the byproduct of a well-built system
Name everythingUnnamed components do not exist in a shared system
Token everythingHardcoded values are technical debt in design form
One source of truthEvery component lives in the library, nowhere else
Document as you buildA component without usage guidance is a trap for the next designer
Right-size the systemComplexity should match project scope
