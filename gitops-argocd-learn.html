GitOps Core Principles

Git as the Single Source of Truth

GitOps is an operational framework that uses Git repositories as the single source of truth for infrastructure and application code. Commits automatically trigger cluster synchronization.

🎯

Single Source of Truth

Entire application & infrastructure state is stored declaratively in version-controlled Git repositories.

🤖

Automated Pull Sync

Software agents (ArgoCD/FluxCD) running inside the cluster pull updates from Git automatically.

⚡

Continuous Drift Control

Cluster state is continuously monitored. Any manual cluster state drift is automatically detected and reconciled.

📄

Declarative Deployment Models

Desired State vs. Imperative Scripts

Instead of defining step-by-step deployment bash scripts, GitOps manifests declare the exact target state.

# Declarative Kubernetes Deployment (my-app.yaml)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 2   # GitOps agent guarantees exactly 2 pods are running
  template:
    spec:
      containers:
      - name: app
        image: myapp:v2.0

Deployment Reconciliation & Automated Rollbacks

Self-Healing & Instant Recovery

Reconciliation continuously compares the running cluster state against the Git repository. If a pod crashes or someone deletes a resource manually, the GitOps controller self-heals it back to match Git.

💡 Instant Rollbacks: If a bad code release occurs in production, simply execute git revert. The GitOps agent immediately rolls back the live cluster to the previous working commit!
🌐

Environment Management (Dev vs. Prod)

📁 Directory-Based Layout

  • environments/dev/kust.yaml
  • environments/prod/kust.yaml
  • Uses Kustomize or Helm values overrides per environment

🌿 Branch-Based Layout

  • dev branch syncs to Dev K8s Cluster
  • main branch syncs to Production K8s Cluster
  • Promotions handled via Git Pull Requests

ArgoCD Architecture & Features

Declarative GitOps Engine for Kubernetes

ArgoCD is a popular Kubernetes-native continuous delivery controller that monitors Git repositories and synchronizes cluster resources in real time.

📊

Web UI & Visual Tree

Rich web dashboard providing real-time visual health metrics, resource trees, and sync statuses of all K8s workloads.

⚡

Automated Sync Policies

Supports manual sync or automated self-healing sync options with pruning of orphaned resources.

🔐

Multi-Tenant & RBAC

Native integration with SSO providers (OIDC, GitHub, Dex) and fine-grained Role-Based Access Control.

GitLab CI/CD Pipeline Manifest Sample

Complete Production 5-Stage `.gitlab-ci.yml` Breakdown

Annotated production pipeline covering dependency installation, unit testing, building, Docker-in-Docker packaging, and SSH EC2 deployment.

# Complete .gitlab-ci.yml Pipeline
variables:
  IMAGE_NAME: "demo/gitlab"
  IMAGE_TAG: "v2.0"

stages:
  - install
  - test
  - build
  - image_build
  - deploy

# Stage 1: Install Dependencies
install:
  image: node:14-alpine
  stage: install
  script:
    - npm install
  artifacts:
    paths: [node_modules/]

# Stage 2: Testing
test:
  image: node:14-alpine
  stage: test
  script:
    - npm test

# Stage 3: Docker-in-Docker Image Build & Push
image_build:
  image: docker:27.3
  stage: image_build
  services: [docker:27.3-dind]
  script:
    - docker login -u $DOCKER_USER -p $DOCKER_PASS
    - docker build -t $IMAGE_NAME:$IMAGE_TAG .
    - docker push $IMAGE_NAME:$IMAGE_TAG

# Stage 4: Deployment over SSH
deploy:
  stage: deploy
  script:
    - ssh -i $SSH_KEY $EC2_USER@$EC2_HOST "docker run -d -p 80:3000 $IMAGE_NAME:$IMAGE_TAG"
