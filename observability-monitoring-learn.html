Observability Fundamentals & 3 Pillars

Monitoring vs. Observability

Monitoring tells you WHAT is failing (e.g. Server down). Observability uses telemetry data to explain WHY it is failing.

📈

1. Metrics

Numerical time-series data measuring system attributes (CPU usage, memory consumption, request throughput).

📜

2. Logs

Timestamped event records generated by applications and system kernels (errors, warnings, user logins).

🔍

3. Traces

End-to-end request journeys tracking a single transaction across multiple distributed microservices.

Prometheus Architecture & TSDB

Pull-Based Metric Scraping Engine

Prometheus periodically scrapes metrics from target endpoints over HTTP, storing data inside an efficient local Time Series Database (TSDB).

🧠

Prometheus Server

Central engine executing metric scraping jobs over HTTP pull model and storing time-series chunks in TSDB.

🎯

Scrape Targets & Exporters

Endpoints exposing metrics under /metrics. Exporters (Node Exporter, MySQL Exporter) expose system metrics.

📤

Pushgateway

Intermediate metrics cache allowing short-lived batch jobs to push metrics to Prometheus.

# prometheus.yml Scrape Configuration
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: "node_exporter"
    static_configs:
      - targets: ["localhost:9100"]
  - job_name: "web_application"
    static_configs:
      - targets: ["localhost:3000"]

Application Performance Monitoring (APM)

Application Code Instrumentation

Expose custom application metrics (response times, active users, DB query counts) using client libraries.

// Express.js Node.js Instrumentation (app.js)
const express = require("express");
const client = require("prom-client");
const app = express();

client.collectDefaultMetrics();   // Collect CPU/RAM default metrics

app.get("/metrics", async (req, res) => {
  res.set("Content-Type", client.register.contentType);
  res.end(await client.register.metrics());
});

app.listen(3000, () => console.log("Server running on port 3000"));

Alerting & Alertmanager Configuration

Deduplicating, Grouping & Routing Alerts

Prometheus fires alerts based on PromQL rule thresholds; Alertmanager routes them to Slack, PagerDuty, or Email.

# alerts.yml Rule Definition
groups:
  - name: system_alerts
    rules:
      - alert: HighCPUUsage
        expr: 100 - (avg by(instance)(irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "High CPU usage detected on {{ $labels.instance }}"

The 4 Golden Signals of SRE Observability

⏱️

1. Latency

The time it takes to service a request (distinguishing successful request latency from error latency).

🌊

2. Traffic

A measure of demand placed on the system (HTTP requests/sec or network I/O bytes/sec).

⚠️

3. Errors

The rate of requests that fail (HTTP 5xx errors or explicit failure responses).

🔋

4. Saturation

How full your system is (CPU load, memory allocation, database connection pool limits).
